# VeganAlts Database Baseline v1.0

## 1. Scope

Cloudflare D1 is the canonical relational database for VeganAlts v1.0. Drizzle ORM should be the application schema/query layer. This document defines the domain model and invariants; the final implementation migration should be generated/reviewed from the Drizzle schema and checked against this baseline.

Better Auth's own tables are generated by Better Auth and are intentionally not hand-maintained in the application baseline. VeganAlts creates a 1:1 application `profiles` record keyed by the Better Auth user ID.

Reference SQL is included at `db/0001_app_baseline.sql`.

## 2. Database principles

1. **Relational integrity first.** Use foreign keys and unique constraints for domain facts that the database can enforce.
2. **Stable opaque IDs.** Use application-generated text IDs (recommended UUIDv7) rather than exposing sequential row IDs.
3. **Country-specific product records.** Market-specific products are separate `products`, optionally linked by `product_families`.
4. **Formula versions are first-class.** Current and historical formulas live in `product_versions`.
5. **Ratings reference formula + category.** Never attach the primary rating only to a product.
6. **Raw data is canonical.** Aggregate/stat tables are derived and rebuildable.
7. **Moderation is additive/versioned.** Protected edits create proposals/history instead of destructive overwrites.
8. **Images live in R2.** D1 stores metadata and object keys only.
9. **Search indexes are derived.** FTS rows can be rebuilt from canonical tables.
10. **Do not split databases by country initially.** Country is data, not infrastructure.

## 3. ID and timestamp conventions

### IDs

Recommended:

```text
UUIDv7 encoded as canonical text
```

Reasons:

- globally unique;
- safe for distributed/client-generated workflows when needed;
- roughly time-sortable;
- not guessable like simple integer IDs;
- easy to use across D1/API/R2 object keys.

Use one ID policy consistently. Do not mix random integer IDs, UUIDs and slugs as primary identifiers.

### Timestamps

Store UTC Unix epoch milliseconds as `INTEGER`.

Application code is responsible for setting timestamps consistently. API serialization may return ISO 8601 strings if preferred, but persistence remains integer milliseconds.

## 4. Core entity model

```text
countries
   │
   ├── categories (hierarchy via parent_id)
   │      └── category_aliases
   │      └── category_rating_dimensions
   │
   ├── products ────── brands
   │      │
   │      ├── product_families
   │      ├── product_versions
   │      ├── product_aliases
   │      ├── product_categories ── categories
   │      ├── product_images
   │      └── product_retailers ── retailers
   │
profiles
   ├── ratings ── product_versions + categories
   │      └── rating_dimension_values
   ├── product_trials
   ├── comments
   ├── retailer_confirmations
   ├── edit_proposals / responses
   └── reports

Derived:
product_category_stats
product_category_daily_stats
search_index
```

## 5. Auth/application identity

### Better Auth tables

Generated and migrated by Better Auth/Drizzle tooling.

### `profiles`

Application-level identity keyed by Better Auth user ID.

Core fields:

- `user_id` — Better Auth user ID;
- `handle` — unique public handle;
- display name/avatar fields if enabled;
- moderation/trust state;
- created/updated timestamps.

Do not store OAuth tokens in the application profile table.

## 6. Countries

`countries` represents market context.

Core fields:

- ISO code;
- display name;
- active flag;
- default locale/currency later if useful.

Country records should be seeded and stable.

## 7. Categories

`categories` is a hierarchy using `parent_id`.

Example:

```text
Food
└── Meat
    └── Beef
        └── Ground Beef
```

Important fields:

- stable ID;
- parent ID;
- canonical slug;
- name;
- `is_rankable`;
- active state.

A parent category such as Beef may exist for discovery without itself being rankable.

### Category aliases

`category_aliases` supports market vocabulary/search terms such as:

```text
Ground Beef ↔ mince
```

Aliases may optionally be country-specific.

### Rating dimensions

`category_rating_dimensions` defines optional detail fields such as Melt/Stretch for Mozzarella.

Dimensions are data-driven so future material categories can use attributes such as Durability/Flexibility without altering the rating schema.

## 8. Brands and product families

### `brands`

Canonical brand identity.

Do not create a new brand record for spelling/casing differences.

### `product_families`

Links conceptually equivalent/related products across markets or records.

Example:

```text
Beyond Beef family
├── US product
└── Canada product
```

A family is organizational; it does not merge rankings across countries.

## 9. Products

`products` is the country-specific commercial identity.

Core fields:

- country;
- brand;
- optional product family;
- canonical name/slug;
- product type;
- lifecycle status;
- VeganAlts vegan status;
- manufacturer label state;
- manufacturer URL where known;
- submitter and timestamps.

### Product types

Initial enum should support at least:

```text
packaged_food
restaurant_item
recipe
material
```

Only `packaged_food` needs to be enabled in the initial product UI. The broader type prevents schema redesign later.

### Lifecycle

Suggested values:

```text
active
under_review
discontinued
hidden
```

`hidden` is an administrative state, not a substitute for deletion/audit history.

### Vegan status

Suggested values:

```text
vegan
appears_vegan
plant_based
under_review
```

Manufacturer labeling is a separate field.

## 10. Product versions

`product_versions` represents materially different formulas.

Core fields:

- product ID;
- label/sequence description;
- effective date range if known;
- `is_current`;
- change summary;
- created/verified metadata.

### Invariant

At most one current version per product.

Use a partial unique index on `product_id WHERE is_current = 1`.

Packaging-only updates do not require a new version unless they correspond to a material formula change. Canonical media can still be updated while keeping the same version.

## 11. Product-category membership

`product_categories` connects products to replacement categories.

Fields include:

- product;
- category;
- `ranking_eligible`;
- created/updated metadata.

One product can belong to multiple categories. Ratings remain category-specific.

Specialty-flavor variants can exist as products without being ranking-eligible for the plain/general category.

## 12. Product relationships / variants

`product_relationships` links related country-local product records without conflating them.

Possible relationship types:

```text
variant
specialty_flavor
companion
successor
```

This supports detail-page “Other variants” sections while preserving separate ranking identity where appropriate.

## 13. Ratings

`ratings` is the canonical primary similarity contribution.

Unique key:

```text
(user_id, product_version_id, category_id)
```

Fields:

- 1–5 `overall_similarity`;
- optional conventional-product recency bucket;
- counted/excluded state;
- timestamps.

The application validates that the product version's product is actually a member of the category and market before accepting a rating.

### Rating moderation

Use `is_counted` plus moderation metadata rather than deleting suspicious ratings immediately.

## 14. Detailed rating values

`rating_dimension_values` stores one 1–5 score for a configured category dimension.

Primary key:

```text
(rating_id, dimension_id)
```

Server validation must ensure the dimension belongs to the same category as the rating.

## 15. Tried state

`product_trials` records that a user has tried a particular formula version.

This is version-specific but not inherently category-specific.

Submitting a rating should upsert the corresponding trial.

Standalone Tried UI may be deferred without removing the underlying capability.

## 16. Ranking aggregates

`product_category_stats` is the fast current read model.

Composite identity:

```text
(product_version_id, category_id)
```

Suggested fields:

- `rating_count`;
- `rating_sum`;
- `raw_average`;
- `bayesian_score`;
- `tried_count`;
- `recent_rating_count`;
- `trending_score`;
- `recomputed_at`.

The row is derived. Never store information here that cannot be reconstructed.

### Daily stats

`product_category_daily_stats` can support trending/history with one row per date/version/category.

This table may be populated only once Trending work begins.

## 17. Comments

`comments` belongs to a product version so comments about an old formula do not silently describe a new formula forever.

An optional category ID can provide context when a comment is specifically about one replacement use.

Include moderation state and soft-delete timestamp rather than destructive deletion for moderated content where appropriate.

## 18. Retailers

### `retailers`

Global canonical retailer identity.

### `retailer_markets`

Declares which countries the retailer operates in and market-specific site/name details if needed.

### `product_retailers`

Connects a country-specific product to a retailer with a “commonly found” relationship.

Suggested status:

```text
active
uncertain
not_current
```

### `retailer_confirmations`

Records independent user confirmations/disagreements over availability.

This is not live inventory.

## 19. Images

`product_images` stores metadata for R2 objects.

Fields include:

- product version;
- slot (`front`, `back`, `ingredients`, `nutrition`, `prepared`);
- state (`pending`, `accepted`, `rejected`, `archived`);
- full/thumbnail R2 keys;
- dimensions;
- contributor;
- timestamps.

Use a partial unique index to ensure only one accepted/current image per version/slot where appropriate.

Historical accepted images may be archived rather than deleted.

## 20. Edit proposals

`edit_proposals` stores structured proposed factual changes.

Use JSON for `proposed_data` because proposal shapes vary by change type, but do not use JSON as an excuse to make canonical product tables schema-less.

Core fields:

- target type/id;
- change type;
- risk tier;
- proposal data;
- note;
- state;
- submitter;
- resolution fields.

## 21. Proposal responses

`edit_proposal_responses` records one current stance per user/proposal:

```text
confirm
disagree
evidence
```

Additional evidence references may be represented in structured JSON/media links initially.

## 22. Reports

`reports` supports product/photo/comment/edit-proposal targets.

Fields:

- reporter;
- target type/id;
- reason code;
- note;
- status;
- resolution metadata.

Report counts alone should not directly change canonical data.

## 23. Audit log

`audit_log` records material accepted moderation/admin changes.

Store structured before/after JSON where appropriate, source proposal/report IDs and the actor/resolver.

The audit log is append-only from normal application code.

## 24. Search index

D1 FTS5 virtual table contains derived searchable documents.

Recommended columns:

- entity type;
- entity ID;
- country code;
- title;
- subtitle/brand;
- aliases;
- body/category ancestry.

Application/domain jobs maintain/rebuild this index.

## 25. Index strategy

At minimum index:

- product by country + lifecycle;
- product by country + slug;
- category parent + active;
- current formula by product;
- product-category by category + eligible;
- ratings by version + category + counted;
- ratings by user + updated time;
- comments by version + created time;
- retailer relationships by product;
- pending proposals by status/risk/created;
- reports by status/created;
- audit by entity type/id/time.

Add indexes based on measured query plans; avoid speculative index explosion because D1 writes update indexes too.

## 26. Delete policy

Prefer lifecycle/status changes and history preservation over physical deletion for established domain records.

Physical deletion is reasonable for:

- failed temporary uploads;
- never-published malformed records;
- certain privacy/account deletion data where legally/product-required;
- derived/search/aggregate rows that can be rebuilt.

When deleting a user/account, preserve community data only according to the final privacy policy and product/legal decisions; do not assume all contributions can remain personally attributable.

## 27. Migration policy

- Every schema change is a migration committed to source control.
- Never edit a previously-applied production migration.
- Prefer additive changes.
- For risky migrations, create new table/copy/verify/swap rather than depending on unsupported SQLite alterations.
- Test migrations against representative seed data.
- Back up/export before destructive production migrations.
- Better Auth migrations and application migrations must have explicit ordering.

Recommended ordering at initial setup:

1. Better Auth schema migration.
2. VeganAlts application baseline.
3. Seed countries/categories/initial brands/products.

**Version 1 baseline (owner decision, 2026-10-10).** Before the first release, the pre-release migrations `0000`–`0020` were folded into one executable baseline, `db/migrations/0001_initial.sql`. It produces exactly the schema those migrations produced (tables, indexes, triggers, the FTS5 index), plus the rows they inserted: the `veganalts-system` actor and the shared allergen list. Every database is created from it; local, staging and production databases carrying the old history are emptied (`npm run db:reset:<env>`) and migrated again rather than upgraded. Until the first release, schema changes are folded into version 1 and every database is reset (owner decision, 2026-10-13); migrations are append-only from the first release on. The milestone sections below keep their original migration names as the record of when each part of the schema was decided; the backfills and upgrade preflights they describe applied only to the old history.

## 28. D1-specific notes

D1 supports foreign keys and FTS5. Use D1 batch operations for groups of statements that need atomic behavior; do not assume interactive database transactions are available in the same way as traditional PostgreSQL clients.

If global read replication is later enabled, use the D1 Sessions API as required by Cloudflare to get replica behavior/consistency correctly.

## 29. Deferred tables/features

Not required in the initial baseline unless implementation makes them immediately useful:

- creator/editorial collections;
- sponsored placements;
- recipe-specific structured data;
- restaurant chain/location integrations;
- notification subscriptions;
- saved/favorite lists;
- barcode identifiers;
- native-device tokens;
- business/brand claim records.

Add these through migrations when their milestone begins.

## Milestone 3 persistence decisions

The approved [milestone specification](MILESTONE_3_PLAN.md) adds operational submission/upload receipts, bounded quotas/leases, held payloads, formula classifications and evidence, canonical aliases, and reversible duplicate archival. Proposed catalog payloads are persisted only for manual review; operational hashes/leases are not canonical products. R2 promotion and D1 publication use a recoverable workflow because they are not one distributed transaction. Formula classifications preserve historical uncertainty; product classification columns project the current formula. Duplicate donors retain all original records and bytes without transfer to the survivor. Preserve canonical references during cleanup and record before/after/resolution provenance for every protected change.

Migration `0008_submission_followups.sql` adds a unique, nullable `pending_submissions.superseded_by` foreign key to the revised receipt. The old payload remains unchanged and its `resolved_at` closes the queue item; its receipt stays in review storage until normal expiry to preserve private evidence. Publication and response finalization both fence against the original revision and unresolved state. Contributor amendments use `submission_amended` audit entries, distinct from operator `submission_follow_up` requests.

Migration `0009_proposal_baselines.sql` adds nullable `edit_proposals.baseline_data`: the catalog facts a proposal was drafted against (current formula, lifecycle, classification, affected photo slots, relationships or retailer status, depending on its kind). Acceptance compares those facts instead of the whole product revision, so unrelated activity never strands a proposal. Proposals created before this migration keep the strict revision comparison.

Migration `0006` once needed a legacy-report preflight and a later identity-key normalization for databases created by earlier releases. Both were removed with the version 1 baseline, since no database carries that history; names and identity keys are always written by the application rules.

## Milestone 4 persistence decisions

The approved [milestone 4 specification](MILESTONE_4_PLAN.md) adds the following append-only migrations.

- `0010_moderation_decisions.sql` records each automated evaluation: subject, kind, schema and policy versions, provider, model, input hash, charged account, status, outcome, structured probabilities, tokens, latency and lease. A check constraint prevents a failed, disabled or over-budget evaluation from carrying an approving outcome. Budget and concurrency accounting is derived from these rows atomically.
- `0011_comment_votes.sql` rebuilds the previously unused, empty `comments` table and replaces the unused helpful-only `comment_reactions` with `comment_votes`. Comments keep their formula and optional category, add a denormalized `product_id` for product-level lists, the states `pending`, `visible`, `hidden` and `removed`, up/down counts, a Best rank derived from the Wilson lower bound, a vote revision compare-and-swap with a per-attempt token that guards the voter's row in the same batch, and edit timestamps. `comment_votes` keeps one row per comment and account with value `1` or `-1`. The migration and the migration command preflight both refuse to proceed if either old table contains rows.
- `0012_system_actor.sql` inserts one data row in Better Auth's `user` table and its profile for automated actions (`veganalts-system`, an unroutable `.invalid` email and no linked sign-in account). This is not an auth schema change; it lets automatic acceptance use the existing audited `moderation_actions` path.
- `0013_proposal_confidence.sql` adds confirm, disagree and evidence counts to `edit_proposals` (recomputed from `edit_proposal_responses` by each response write; confidence is derived from them) and an index on `moderation_actions(actor_id, created_at)`.
- `0014_category_taxonomy.sql` adds category revisions, `category_proposals`, `category_slug_history` (former slugs redirect), `category_merges` (resumable transfer state, finalize data for children, aliases and features) with the `category_merge_moves` ledger (every rating, membership and comment a merge changed and its prior counted/eligibility values), and `category_features` (homepage merchandising), backfilled from the former hard-coded list. The production-safe taxonomy seed lives in `db/seed/taxonomy.ts` and `npm run taxonomy:seed:<environment>`; production additionally requires `--confirm-taxonomy-only`.
- `0015_trending_reads.sql` adds `product_category_trends` and the indexes that keep Trending and New reads off raw ratings.

`product_category_stats.trending_score` remains unused because rating writes replace those rows; trends are stored separately and rebuilt from daily statistics. Daily statistics and trends are derived and reproducible.

## Milestone 5 persistence decisions

The approved [milestone 5 specification](MILESTONE_5_PLAN.md) adds the following append-only migrations and rules.

- `0016_markets_allergens.sql`
  - Adds `ix_retailer_markets_country(country_id, is_active, retailer_id)` for the store filter.
  - Adds `allergens(key, label)`, the shared allergen vocabulary, inserted by the migration: milk, egg, fish, crustacean, mollusc, tree_nuts, peanut, wheat, gluten, soy, sesame, mustard, celery, lupin, sulphites.
  - Adds `country_allergens(country_id, allergen_key, position, label)`, each country's declared-allergen list with optional local wording, written by the taxonomy seed.
  - Adds `product_version_allergen_declarations`: one row per formula version, status `declared` or `none_declared`, evidence and source proposal.
  - Adds `product_version_allergens(product_version_id, allergen_key, presence)`, where presence is `contains` or `may_contain`.
  - Triggers require allergen rows to belong to a `declared` declaration, with a key on the product country's list, and bump `catalog_revisions` on every change.
  - Absence of a declaration means "not confirmed"; only accepted proposals write declarations.
- `0017_taxonomy_shape.sql` adds `category_aliases.is_display_name`. A display name must be country-scoped, and each food has at most one display name per country. Food names render as that alias in its country; slugs never change.
- `0018_detail_scores.sql`
  - Adds `product_category_dimension_stats(product_version_id, category_id, dimension_id, answer_count, answer_sum)`.
  - Adds `product_category_familiarity_stats(product_version_id, category_id, recency, overall_similarity, rating_count)`, where `recency` is one of the five `ratings.conventional_recency` buckets or `unanswered`.
  - Both are derived from counted ratings, written in the rating batch and rebuilt by the integrity rebuild.
  - Rebuilds the empty-dependency `category_merge_moves` ledger so merges can record dimension rows.
  - Adds a trigger that moves a rating's detail answers to the same-key dimension when the rating changes category, and refuses the change if no such dimension exists.
  - Adds a trigger that fixes a dimension's key and category once created.
  - Adds triggers that bump the formula revision whenever a detail answer changes, so concurrent rating writers retry.
  - Backfills familiarity rows (recency `unanswered`) for existing counted ratings. The taxonomy seed, not the migration, gives foods without questions their launch list or Taste and Texture.

**Taxonomy shape.** Depth is computed from `parent_id`, not stored: aisles are children of the root, shelves are children of aisles, and rankable foods are children of shelves. Food names and all aliases remain unique across the taxonomy (case-, accent- and spacing-insensitive); group names are unique among siblings and groups have no aliases. Slugs remain globally unique. Every new rankable category starts with Taste and Texture dimensions.

**Countries.** The taxonomy seed inserts the six launch countries as active rows (generated IDs on staging and production; the local development catalog seed uses deterministic IDs such as `country:US`), their allergen lists, homepage features and display names. Rows are matched by ISO code, never by ID. It stays insert-only and idempotent. Existing local and staging data are re-parented to the three-level shape by `scripts/reshape-taxonomy.ts`, which uses the audited, reversible taxonomy update path. Product slugs are unique per country, so every product read is scoped by country.

## Milestone 6 persistence decisions

The approved [milestone 6 specification](MILESTONE_6_PLAN.md) adds the following append-only, additive migrations. No parent table is rebuilt: D1 cannot disable foreign keys, so rebuilding `products` would cascade into ratings (see `0006`).

- `0019_country_foods.sql`
  - Adds `category_countries(category_id, country_id, source, created_by, created_at)` with primary key `(category_id, country_id)` and an index on `(country_id, category_id)`. `source` is `launch`, `proposal`, `product` or `operator`.
  - Backfills every active rankable food in every active country, plus every (food, country) pair of a visible product.
  - Triggers enforce the invariants:
    - only rankable categories (foods) get rows;
    - a row cannot be deleted while the food has a visible product in that country;
    - inserting a `product_categories` row switches the food on in the product's country (covering publication, category additions and merges);
    - restoring a hidden product switches its foods on again.
- `0020_quick_additions.sql`
  - Adds `formula_classifications.ingredients_checked` (`1` by default). A check allows `0` only with the placeholder status `appears_vegan`, so an unchecked formula can never be stored as Vegan or Under Review.
  - Adds `pending_submissions.category_proposal_id`, referencing `category_proposals`, with a partial index. A held submission that suggested a food points at that suggestion.

**Foods per country.** Aisles and shelves are never country-scoped. Public reads list a food in a country only when it has a `category_countries` row there; groups without such a food are hidden. A food stays on wherever it has a visible product. Activating a new country switches no foods on. The taxonomy seed writes launch availability only for foods that have none, so an operator's choices are never overwritten.

**Ingredients not checked.** The public classification is derived by one shared read helper: `ingredients_checked = 0` reads as `unchecked`, otherwise the stored status. Writers never store `unchecked`. Any reviewed classification sets the flag to `1`, and reversal restores both values.

**Starter shelves.** The taxonomy seed adds the Fish and seafood aisle (`fish-and-seafood`) and the shelves `turkey-shelf`, `lamb-shelf`, `fish-shelf`, `shellfish-shelf`, `cream-shelf`, `yogurt-shelf`, `ice-cream-shelf` and `hard-and-grated`, insert-only by slug.

## Milestone 7 persistence decisions

The [milestone 7 specification](MILESTONE_7_PLAN.md) adds the following. They were built as migrations `0002`–`0004` and folded into version 1, `0001_initial.sql`, before staging (owner decision, 2026-10-12). Every database is reset to version 1, so their backfills went with them. The folded file produces exactly the schema the four migrations produced.

- **Aisle order and seasons**
  - Adds `categories.position`, the default order of an aisle where a country has no ratings yet, seeded for every aisle.
  - Adds `categories.season_start` and `categories.season_end`, both months 1–12; a season may wrap past December. Both are null for a food without a season, and a check keeps them both set or both null.
  - Adds `products.seasonal` (0 or 1).
- **Recipe lines**
  - **Columns.** Adds `products.flavor`, `product_families.country_id` and `ratings.enjoyment`. Adds `enjoyment_count`, `enjoyment_sum` and `enjoyment_score` to `product_category_stats`. `product_families.country_id` allows NULL only because it joined the table later; a trigger requires it on every new line.
  - **Writers.** A submission outside a chosen line starts its own line in the same batch, and a chosen line must have the product's brand and country. A relationships proposal without a line keeps the product's current one.
  - **Triggers** enforce:
    - a product is inserted with a family and can never lose it;
    - a product's brand and country equal its family's;
    - a family with products cannot be deleted;
    - a flavor is trimmed, not blank and at most 40 characters;
    - enjoyment is between 1 and 5.
  - **`family_category_stats`** has one row per family and food, holding:
    - for Closest and for Tastiest: people, the sum of per-person means, the raw mean and the Bayesian score;
    - tried and recent people;
    - the lead product.
  - **`family_category_dimension_stats`** has one row per family, food and dimension: people who answered and the sum of their means.
  - **Indexes:** `products(product_family_id)` for a line's flavors, `product_families(brand_id, country_id)` for a brand's lines, and the existing `products(brand_id, country_id)` for brand pages.
- **Line discovery**
  - Adds `family_category_daily_stats`, one row per line, food, day and person over the last 180 days (the 90-day trend window and its baseline), so Trending counts each person once across the window. A row holds that day's counted ratings of the line's eligible flavors and their similarity sum, and whether the person tried a flavor or left a visible comment.
  - Adds `family_category_trends`, with each trending line's `rank` in its food. The top three carry the Trending tag.
  - Adds `family_category_first_published`: when a line first appeared in a food, from any flavor it has had there. Refreshes only move it earlier, so New never brings a line back.
  - Removes `product_category_daily_stats`, `product_category_trends` and the unused `product_category_stats.trending_score` with its index. All three were derived and are no longer read.

**Product family.** A family is a recipe line in one country: one brand's base recipe and its flavors. It no longer links markets. Rankings group a food's eligible products by family.

**Taxonomy shape.** This replaces milestone 5's three-level shape and milestone 6's starter shelves.

- **Depth.** Aisles are children of the root and foods are children of aisles.
- **Seed.** The taxonomy seed writes the aisles and the launch foods.
- **Availability.** `TAXONOMY_LEAVES` carries an optional `countries` list for launch availability.
- **Existing environments.** For an environment that is not reset, the reshape script re-parents foods to aisles through the audited taxonomy path and retires the emptied shelves.

**Review fixes, folded into version 1 (owner decision, 2026-10-13).**

- **Seed processing.** `media_attempts.counted` (default 1). Owner-run demo seeding (`scripts/seed-images.ts`) records 0, so a reseed is neither held to nor spends the environment's daily processing allowance that web uploads share; both allowance checks count only `counted=1`.
- **Brand index.** `brand_search` is an FTS5 table with the trigram tokenizer: each brand's name and other names (`names`), and its other names as a JSON array (`aliases`). Triggers on `brands` and `brand_aliases` keep it current in the same transaction as any write, and the search rebuild rewrites it. Brand lookups read candidates sharing three letters in a row with the typed text and, from five letters, brands whose `normalized_name` (or an alias's) starts with a typed word's first letter, through their unique indexes, so they never read every brand.

## Store photo import persistence decisions

The [store photo importer](IMPORTER_PLAN.md) (owner, 2026-10-16) writes no new table and no migration; version 1 is unchanged.

- **Rows.** An imported product has the catalog rows a published submission has: brand, line, product, identity key, formula, food, classification, accepted photos, store confirmations, search documents and line statistics, written by the same statement builder in one transaction. It has no submission receipt, staged photos, media uploads or pending review.
- **Ids.** Product, formula, photo, brand and audit ids are UUIDv5 in the `veganalts:import:` namespace, derived from the product's source key (`<batch folder>/<product id>`), so every environment and every rerun gets the same ids, slugs and photo keys. Lines keep the publication rule, `line-<first product id>`.
- **Photos.** Keys are `products/<product>/<formula>/<image>/import/<kind>.webp`. The image id includes the full copy's SHA-256, so bytes under a referenced key never change. Imported ingredients and nutrition photos have no evidence copy (`evidence_r2_key` is null): their 1,800 px full copy is the most readable version kept.
- **Idempotency.** Each product commits a `contribution_receipts` row (operation `catalog-import`) whose hash covers its site facts. A rerun replays it; changed facts are reported and never overwrite the catalog.
- **Audit.** Each product records a `product_import` moderation action (before `{"lifecycleStatus":"hidden"}`, after `{"lifecycleStatus":"active"}`) with its `audit_log` entry, and a `product_published` audit entry holding the run, source key, manifest hash and submission facts. Runs record `catalog_import_started` and `catalog_import_finished` entries (entity type `catalog_import`).

# VeganAlts Database Baseline v1.0

## 1. Scope

Cloudflare D1 is the canonical relational database for VeganAlts v1.0. Drizzle ORM should be the application schema/query layer. This document defines the domain model and invariants; the final implementation migration should be generated/reviewed from the Drizzle schema and checked against this baseline.

Better Auth's own tables are generated by Better Auth and are intentionally not hand-maintained in the application baseline. VeganAlts creates a 1:1 application `profiles` record keyed by the Better Auth user ID.

Reference SQL is included at `db/0001_app_baseline.sql`.

## 2. Database principles

1. **Relational integrity first.** Use foreign keys and unique constraints for domain facts that the database can enforce.
2. **Stable opaque IDs.** Use application-generated text IDs (recommended UUIDv7) rather than exposing sequential row IDs.
3. **Country-specific product records.** Market-specific products are separate `products`, optionally linked by `product_families`.
4. **Formula versions are first-class.** Current and historical formulas live in `product_versions`.
5. **Ratings reference formula + category.** Never attach the primary rating only to a product.
6. **Raw data is canonical.** Aggregate/stat tables are derived and rebuildable.
7. **Moderation is additive/versioned.** Protected edits create proposals/history instead of destructive overwrites.
8. **Images live in R2.** D1 stores metadata and object keys only.
9. **Search indexes are derived.** FTS rows can be rebuilt from canonical tables.
10. **Do not split databases by country initially.** Country is data, not infrastructure.

## 3. ID and timestamp conventions

### IDs

Recommended:

```text
UUIDv7 encoded as canonical text
```

Reasons:

- globally unique;
- safe for distributed/client-generated workflows when needed;
- roughly time-sortable;
- not guessable like simple integer IDs;
- easy to use across D1/API/R2 object keys.

Use one ID policy consistently. Do not mix random integer IDs, UUIDs and slugs as primary identifiers.

### Timestamps

Store UTC Unix epoch milliseconds as `INTEGER`.

Application code is responsible for setting timestamps consistently. API serialization may return ISO 8601 strings if preferred, but persistence remains integer milliseconds.

## 4. Core entity model

```text
countries
   │
   ├── categories (hierarchy via parent_id)
   │      └── category_aliases
   │      └── category_rating_dimensions
   │
   ├── products ────── brands
   │      │
   │      ├── product_families
   │      ├── product_versions
   │      ├── product_aliases
   │      ├── product_categories ── categories
   │      ├── product_images
   │      └── product_retailers ── retailers
   │
profiles
   ├── ratings ── product_versions + categories
   │      └── rating_dimension_values
   ├── product_trials
   ├── comments
   ├── retailer_confirmations
   ├── edit_proposals / responses
   └── reports

Derived:
product_category_stats
product_category_daily_stats
search_index
```

## 5. Auth/application identity

### Better Auth tables

Generated and migrated by Better Auth/Drizzle tooling.

### `profiles`

Application-level identity keyed by Better Auth user ID.

Core fields:

- `user_id` — Better Auth user ID;
- `handle` — unique public handle;
- display name/avatar fields if enabled;
- moderation/trust state;
- created/updated timestamps.

Do not store OAuth tokens in the application profile table.

## 6. Countries

`countries` represents market context.

Core fields:

- ISO code;
- display name;
- active flag;
- default locale/currency later if useful.

Country records should be seeded and stable.

## 7. Categories

`categories` is a hierarchy using `parent_id`.

Example:

```text
Food
└── Meat
    └── Beef
        └── Ground Beef
```

Important fields:

- stable ID;
- parent ID;
- canonical slug;
- name;
- `is_rankable`;
- active state.

A parent category such as Beef may exist for discovery without itself being rankable.

### Category aliases

`category_aliases` supports market vocabulary/search terms such as:

```text
Ground Beef ↔ mince
```

Aliases may optionally be country-specific.

### Rating dimensions

`category_rating_dimensions` defines optional detail fields such as Melt/Stretch for Mozzarella.

Dimensions are data-driven so future material categories can use attributes such as Durability/Flexibility without altering the rating schema.

## 8. Brands and product families

### `brands`

Canonical brand identity.

Do not create a new brand record for spelling/casing differences.

### `product_families`

Links conceptually equivalent/related products across markets or records.

Example:

```text
Beyond Beef family
├── US product
└── Canada product
```

A family is organizational; it does not merge rankings across countries.

## 9. Products

`products` is the country-specific commercial identity.

Core fields:

- country;
- brand;
- optional product family;
- canonical name/slug;
- product type;
- lifecycle status;
- VeganAlts vegan status;
- manufacturer label state;
- manufacturer URL where known;
- submitter and timestamps.

### Product types

Initial enum should support at least:

```text
packaged_food
restaurant_item
recipe
material
```

Only `packaged_food` needs to be enabled in the initial product UI. The broader type prevents schema redesign later.

### Lifecycle

Suggested values:

```text
active
under_review
discontinued
hidden
```

`hidden` is an administrative state, not a substitute for deletion/audit history.

### Vegan status

Suggested values:

```text
vegan
appears_vegan
plant_based
under_review
```

Manufacturer labeling is a separate field.

## 10. Product versions

`product_versions` represents materially different formulas.

Core fields:

- product ID;
- label/sequence description;
- effective date range if known;
- `is_current`;
- change summary;
- created/verified metadata.

### Invariant

At most one current version per product.

Use a partial unique index on `product_id WHERE is_current = 1`.

Packaging-only updates do not require a new version unless they correspond to a material formula change. Canonical media can still be updated while keeping the same version.

## 11. Product-category membership

`product_categories` connects products to replacement categories.

Fields include:

- product;
- category;
- `ranking_eligible`;
- created/updated metadata.

One product can belong to multiple categories. Ratings remain category-specific.

Specialty-flavor variants can exist as products without being ranking-eligible for the plain/general category.

## 12. Product relationships / variants

`product_relationships` links related country-local product records without conflating them.

Possible relationship types:

```text
variant
specialty_flavor
companion
successor
```

This supports detail-page “Other variants” sections while preserving separate ranking identity where appropriate.

## 13. Ratings

`ratings` is the canonical primary similarity contribution.

Unique key:

```text
(user_id, product_version_id, category_id)
```

Fields:

- 1–5 `overall_similarity`;
- optional conventional-product recency bucket;
- counted/excluded state;
- timestamps.

The application validates that the product version's product is actually a member of the category and market before accepting a rating.

### Rating moderation

Use `is_counted` plus moderation metadata rather than deleting suspicious ratings immediately.

## 14. Detailed rating values

`rating_dimension_values` stores one 1–5 score for a configured category dimension.

Primary key:

```text
(rating_id, dimension_id)
```

Server validation must ensure the dimension belongs to the same category as the rating.

## 15. Tried state

`product_trials` records that a user has tried a particular formula version.

This is version-specific but not inherently category-specific.

Submitting a rating should upsert the corresponding trial.

Standalone Tried UI may be deferred without removing the underlying capability.

## 16. Ranking aggregates

`product_category_stats` is the fast current read model.

Composite identity:

```text
(product_version_id, category_id)
```

Suggested fields:

- `rating_count`;
- `rating_sum`;
- `raw_average`;
- `bayesian_score`;
- `tried_count`;
- `recent_rating_count`;
- `trending_score`;
- `recomputed_at`.

The row is derived. Never store information here that cannot be reconstructed.

### Daily stats

`product_category_daily_stats` can support trending/history with one row per date/version/category.

This table may be populated only once Trending work begins.

## 17. Comments

`comments` belongs to a product version so comments about an old formula do not silently describe a new formula forever.

An optional category ID can provide context when a comment is specifically about one replacement use.

Include moderation state and soft-delete timestamp rather than destructive deletion for moderated content where appropriate.

## 18. Retailers

### `retailers`

Global canonical retailer identity.

### `retailer_markets`

Declares which countries the retailer operates in and market-specific site/name details if needed.

### `product_retailers`

Connects a country-specific product to a retailer with a “commonly found” relationship.

Suggested status:

```text
active
uncertain
not_current
```

### `retailer_confirmations`

Records independent user confirmations/disagreements over availability.

This is not live inventory.

## 19. Images

`product_images` stores metadata for R2 objects.

Fields include:

- product version;
- slot (`front`, `back`, `ingredients`, `nutrition`, `prepared`);
- state (`pending`, `accepted`, `rejected`, `archived`);
- full/thumbnail R2 keys;
- dimensions;
- contributor;
- timestamps.

Use a partial unique index to ensure only one accepted/current image per version/slot where appropriate.

Historical accepted images may be archived rather than deleted.

## 20. Edit proposals

`edit_proposals` stores structured proposed factual changes.

Use JSON for `proposed_data` because proposal shapes vary by change type, but do not use JSON as an excuse to make canonical product tables schema-less.

Core fields:

- target type/id;
- change type;
- risk tier;
- proposal data;
- note;
- state;
- submitter;
- resolution fields.

## 21. Proposal responses

`edit_proposal_responses` records one current stance per user/proposal:

```text
confirm
disagree
evidence
```

Additional evidence references may be represented in structured JSON/media links initially.

## 22. Reports

`reports` supports product/photo/comment/edit-proposal targets.

Fields:

- reporter;
- target type/id;
- reason code;
- note;
- status;
- resolution metadata.

Report counts alone should not directly change canonical data.

## 23. Audit log

`audit_log` records material accepted moderation/admin changes.

Store structured before/after JSON where appropriate, source proposal/report IDs and the actor/resolver.

The audit log is append-only from normal application code.

## 24. Search index

D1 FTS5 virtual table contains derived searchable documents.

Recommended columns:

- entity type;
- entity ID;
- country code;
- title;
- subtitle/brand;
- aliases;
- body/category ancestry.

Application/domain jobs maintain/rebuild this index.

## 25. Index strategy

At minimum index:

- product by country + lifecycle;
- product by country + slug;
- category parent + active;
- current formula by product;
- product-category by category + eligible;
- ratings by version + category + counted;
- ratings by user + updated time;
- comments by version + created time;
- retailer relationships by product;
- pending proposals by status/risk/created;
- reports by status/created;
- audit by entity type/id/time.

Add indexes based on measured query plans; avoid speculative index explosion because D1 writes update indexes too.

## 26. Delete policy

Prefer lifecycle/status changes and history preservation over physical deletion for established domain records.

Physical deletion is reasonable for:

- failed temporary uploads;
- never-published malformed records;
- certain privacy/account deletion data where legally/product-required;
- derived/search/aggregate rows that can be rebuilt.

When deleting a user/account, preserve community data only according to the final privacy policy and product/legal decisions; do not assume all contributions can remain personally attributable.

## 27. Migration policy

- Every schema change is a migration committed to source control.
- Never edit a previously-applied production migration.
- Prefer additive changes.
- For risky migrations, create new table/copy/verify/swap rather than depending on unsupported SQLite alterations.
- Test migrations against representative seed data.
- Back up/export before destructive production migrations.
- Better Auth migrations and application migrations must have explicit ordering.

Recommended ordering at initial setup:

1. Better Auth schema migration.
2. VeganAlts application baseline.
3. Seed countries/categories/initial brands/products.

## 28. D1-specific notes

D1 supports foreign keys and FTS5. Use D1 batch operations for groups of statements that need atomic behavior; do not assume interactive database transactions are available in the same way as traditional PostgreSQL clients.

If global read replication is later enabled, use the D1 Sessions API as required by Cloudflare to get replica behavior/consistency correctly.

## 29. Deferred tables/features

Not required in the initial baseline unless implementation makes them immediately useful:

- creator/editorial collections;
- sponsored placements;
- recipe-specific structured data;
- restaurant chain/location integrations;
- notification subscriptions;
- saved/favorite lists;
- barcode identifiers;
- native-device tokens;
- business/brand claim records.

Add these through migrations when their milestone begins.
